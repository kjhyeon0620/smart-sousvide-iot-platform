# AI Collaboration: 완료 보고 형식

AI 에이전트(Claude, Codex 등)가 작업을 마칠 때 제공하는 산출물 형식을 정한다.
작업 절차는 [`docs/specs/README.md`](specs/README.md), Git과 GitHub 규칙은 [`AGENTS.md`](../AGENTS.md)를 따른다.

## 1. 작업 단위 보고 (매 작업 종료 시)

1. **변경 파일**: 수정하거나 추가한 파일
2. **구현 방식**: 흐름과 구조 (What / How)
3. **설계 이유**: 선택한 근거와 검토한 대안 (Why). 필요하면 Port/Adapter, 장애 격리, 확장성 관점을 포함한다
4. **리스크**: 잠재 리스크와 영향 범위
5. **테스트 결과**: 실행한 명령, 통과·실패 여부, 핵심 로그 요약
6. **스펙 상태**: 스펙에서 갱신한 섹션 (Decisions, status), 새로 생긴 Open 질문

## 2. 커밋 전 보고

구현과 검증이 끝나면 **커밋하지 않은 상태로 작업 요약(1장 형식)만** 보고하고 승인을 기다린다.
커밋 메시지, PR 제목·본문 초안은 보고하지 않는다. 승인 후 에이전트가 [`AGENTS.md` §3.1](../AGENTS.md) 규칙(템플릿, 최근 이력)대로 작성해 커밋, 푸시, PR 생성까지 한다.

보고 전에 스펙의 `회고` 섹션을 먼저 채운다.

블로그 팩트 리포트(3장)는 사용자가 요청할 때 작성한다. Problem과 Lesson은 스펙의 회고를 입력으로 쓴다.

## 3. 블로그 팩트 리포트

`Context / Problem / Solution / Key Code / Lesson` 5개 섹션을 유지한다.

| 섹션 | 최소 분량 |
|---|---|
| Context | 1~2문장. 왜 필요한 작업이었는가 |
| Problem | 구체적인 상황(에러, 비효율, 리스크) 2개 이상 |
| Solution | 의사결정 근거를 포함한 3문장 이상 |
| Key Code | 핵심 로직 코드 블록 1개 이상 |
| Lesson | 일반화할 수 있는 인사이트 2개 이상 (회고의 "고친 위치" 포함) |

- 취재 기자처럼 과장 없이 사실 중심으로 쓴다. 코드와 측정 결과로 입증할 수 있는 내용만 쓴다.
- 코드를 나열하기보다 문제 해결의 맥락을 연결한다.
- 같은 템플릿을 다시 요청받으면 처음과 같거나 더 높은 밀도로 다시 작성한다.

## 4. 품질 기준

- 모호한 표현 대신 측정할 수 있는 완료 기준을 쓴다.
- 파싱 실패, 저장 실패, 재시도, 관측성(로그, 메트릭) 관점을 항상 포함한다.
- 고트래픽과 운영 안정성 관점에서 쓴다.
