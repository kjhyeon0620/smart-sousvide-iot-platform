# ADR-0005: Timestral 도입 보류, 기기 이상 탐지는 규칙 기반

## Status
Accepted (#74)

## Context
- 지금은 기기가 offline일 때만 감지한다. online인데 목표 온도를 유지하지 못하거나 센서가 멈춘 상태는 알 수 없다.
- Mistral이 시계열 파운데이션 모델 Timestral(5M~209M, CPU 추론, zero-shot, 21개 분위수 예측)을 공개했다. 예측 구간 밖을 이상으로 보는 방식과 예열 완료 ETA에 쓸 수 있는지 검토했다.
- 운영 서버(oci1)는 ARM Neoverse-N1 2코어, RAM 11Gi, swap 없음이다. Spring, MySQL, Influx, k3s가 같은 노드에서 돈다.
- 실제 기기 데이터가 없어 sous-vide 물리 시뮬레이터(1차 열 모델, 히스테리시스 제어, 센서 노이즈)로 비교했다.

## Decision
- **Timestral을 지금은 도입하지 않는다.** 실시간 이상 탐지와 예열 ETA 모두에 해당한다.
- 기기 이상 탐지는 **규칙 기반 순수 로직**으로 구현한다: 목표 이탈, 가열 정체, 센서 고착. 구현은 #75에서 한다.
- 모델 추론이 필요해지면 ingestion 경로가 아니라 별도 사이드카(k3s 파드, CPU·메모리 limit)로 둔다.

## Alternatives
- **Timestral 예측 구간 기반 이상 탐지**: 고장 주입 실험에서 규칙보다 탐지율이 낮고 오탐이 많았다.

  | 경우 | 규칙 | Timestral-5M | Timestral-28M |
  |---|---|---|---|
  | 정상 데이터 오탐 | 0% | 42% | 25% |
  | 히터 열화 탐지 | 50% | 35% | 28% |
  | 센서 고착 탐지 | 100% | 15% | 12% |
  | 뚜껑 열림 탐지 | 95% | 85% | 88% |

  제어되는 신호라 "정상이면 목표 근처"라는 답이 이미 있고, 규칙이 이를 직접 쓴다. 센서 고착은 고정값이 예측 구간 안에 머물러 예측 방식으로는 원리상 잡기 어렵다.
- **Timestral 예열 ETA**: 가열 10~20분 시점에서만 직선·지수 피팅보다 나았다(MAE 11~15분 vs 20~24분). 5분 시점은 실패가 잦았고, 30분 이후는 지수 피팅이 더 정확했다. 10~20분 시점에는 예측 구간 상한이 거의 정해지지 않아 범위 표시도 어려웠다.
- **더 큰 모델(123M/209M)**: oci1에서 기기당 0.7~4.3초로 느리고, 정확도도 5M/28M 대비 크게 낫지 않았다.

## Consequences
- 장점:
  - Python 런타임과 사이드카 없이 Java 순수 로직으로 해결한다. 배포 구성이 늘지 않는다.
  - 규칙은 결과를 설명하기 쉽고(무엇이 몇 분 동안 어땠는지), 단위 테스트로 고정할 수 있다.
- 감수하는 점:
  - 규칙은 정해 둔 패턴만 잡는다. 히터 열화처럼 온도로 드러나지 않는 느린 변화는 규칙도 절반만 잡았다.
  - 비교가 시뮬레이션 기준이고, 규칙 임계값도 시뮬레이터를 보고 정해 규칙에 유리하다. 실제 기기에서 다시 확인해야 한다.

## Revisit When
- 운영 데이터에서 규칙이 놓치는 이상이 반복해서 확인될 때. 후보는 실시간 판정이 아니라 듀티비·가열 속도 같은 파생 지표의 일 단위 드리프트 감지다.
- 실사용 트래픽이 생겨 운영 메트릭(수신량, 지연)에 일·주 주기가 생길 때. 고정 임계값보다 예측 구간 방식이 나을 수 있는 영역이다.
- 기기별 예열 이력이 쌓였는데 기기별 열 특성 학습 ETA로도 정확도가 부족할 때.
- 추론 서버 사양이 바뀔 때(코어 수 증가, GPU).
