# ADR-0005 자료: Timestral PoC 결과 (2026-10-20)

Mistral Timestral(시계열 파운데이션 모델, 2026-10-15 공개)을 sous-vide 텔레메트리 이상 탐지와 예열 ETA에 쓸 수 있는지 검토한 기록.
결정은 [ADR-0005](../0005-timestral-anomaly-detection-deferred.md), 이슈는 #74.

## 1. 배경
- Timestral은 **예측 모델**이다. 이상 탐지 기능은 없고, 21개 분위수(0.01~0.99) 예측 구간 밖을 이상으로 보는 방식으로 직접 구성해야 한다.
- 크기 5M / 28M / 123M / 209M. 공식 지연: 8스레드 서버 CPU에서 15분 간격 3주 → 1일 예측이 5M 10ms, 209M 140ms. GPU 불필요.
- 출처: https://mistral.ai/news/timestral/ , https://ai-tldr.dev/models/timestral-1-0/ (서드파티)
- 붙인다면 Python 사이드카(k3s 파드)로 Influx를 주기 조회. ingestion 경로에는 넣지 않는다.

## 2. 환경 (oci1, 운영 서버)
| 항목 | 값 |
|---|---|
| CPU | ARM Neoverse-N1 2코어 (aarch64) |
| RAM | 11Gi (사용 가능 8.4Gi), swap 없음 |
| 디스크 여유 | 23G |
| 함께 도는 것 | Spring(java ×2), k3s, MySQL, Influx, next-server |
| 런타임 | Python 3.12.3, torch 2.14.1+cpu, timestral 1.0.0 (`logs/server-env.txt`) |

- 서버에 `python3-venv`/pip가 없어 시스템 패키지 대신 `uv` 단일 바이너리를 `~/timestral-bench/bin`에 설치해 venv를 만들었다. 캐시·가중치도 같은 디렉터리(`HF_HOME`)에 둠.
- 모든 측정은 `nice -n 19`. 1스레드는 `taskset -c 1`.
- HF 저장소 이름: `mistralai/Timestral-{5M,28M,123M,209M}` (실제로 받아짐).

## 3. 과정
1. `scripts/bench.py`: 4개 모델 × 1/2스레드 지연과 peak RSS 측정 (`logs/01-*`, `logs/02-*`).
   - 5M/28M은 배치 32 시나리오 포함. 배치가 시리즈당 시간을 줄이지 않아 123M/209M 재실행 때 배치 32를 제거했다(서버에서 `sed`로 해당 줄 삭제. 여기 사본은 원본).
   - 첫 실행의 정리 단계에서 `pkill -f`가 자기 ssh 세션까지 죽였다(exit 255). 이후 패턴을 `[b]ench.py` 형태로 쓰고 재실행.
2. `scripts/accuracy.py`: `symmetric_averaging` on/off 정확도 비교. 시뮬레이션 64개 시리즈.
   - 209M 측정 중 ssh가 끊겨 결과 없이 종료됨. `nohup` + 서버 로그 파일로 재실행(`logs/acc209.txt`, 2스레드로 변경).
   - 주의: 이 스크립트의 시뮬레이터는 출력 대비 열 손실이 커서 일부 시리즈가 목표 온도에 못 닿는 버그가 있다. `faults.py`에서 고쳤다.
3. `scripts/faults.py`: 고장 주입 후 규칙 vs Timestral 탐지 비교 (`logs/faults.txt`).
4. `scripts/eta.py`: 예열 ETA 비교 (`logs/eta.txt`).

## 4. 결과

### 4.1 지연과 메모리 (oci1)
"우리 조건" = 1분 간격 1일(1440) → 15분 예측, `targetTemp`를 known 공변량으로. "sym"은 대칭평균(기본 on, 추론 2회).

| 모델 | 공식 조건 1T | 우리 조건 1T sym/nosym | 우리 조건 2T nosym | 배치32 시리즈당 1T | peak RSS |
|---|---|---|---|---|---|
| 5M | 72ms | 143 / 72ms | 48ms | 131ms | 0.4GB |
| 28M | 258ms | 594 / 297ms | 184ms | 616ms | 0.6GB |
| 123M | 991ms | 2547 / 1268ms | 686ms | - | 1.2GB |
| 209M | 1728ms | 4321 / 2211ms | 1212ms | - | 1.9GB |

- 공식 수치 대비 5~12배 느림 (2코어 ARM).
- 배치로 묶어도 처리량이 늘지 않는다.
- 감당 규모(5M, nosym, 1T): 1천 대 ≈ 72초/회, 1만 대 ≈ 12분/회.

### 4.2 대칭평균 on/off 정확도 (시뮬레이션 64개)
| 모델 | MAE sym → nosym | 98% 구간 적중률 sym → nosym | 98% 구간 폭 |
|---|---|---|---|
| 5M | 0.228 → 0.232℃ | 97.7 → 97.3% | 1.81 → 1.79℃ |
| 28M | 0.220 → 0.222℃ | 97.5 → 97.1% | 1.53 → 1.51℃ |
| 123M | 0.196 → 0.199℃ | 97.7 → 98.2% | 1.42 → 1.42℃ |
| 209M | 0.204 → 0.204℃ | 97.1 → 96.2% | 1.45 → 1.37℃ |

- 대칭평균을 꺼도 정확도 차이는 무시할 수준이고 속도는 2배. 끄는 쪽이 맞다.
- 209M은 123M보다 낫지 않았다.

### 4.3 고장 주입: 규칙 vs Timestral
설계:
- 시리즈 160개(정상 40 + 고장 3종 × 40). 1일 이력 + 2시간 평가 구간. 정상의 30%는 평가 구간 안에서 목표 온도 ±3℃ 변경.
- 고장: 히터 열화(출력 50%), 센서 고착(값 고정), 뚜껑 열림(20분간 열 손실 4배). 고장 시작은 평가 구간 15~90분 사이.
- 규칙(하나라도 걸리면 알림): |temp−target| > 1℃ 3분 연속(설정 변경 후 30분 유예) / HEATING 10분인데 온도 상승 없음 / 10개 연속 같은 값.
- Timestral(nosym): 15분마다 15분 예측, 98% 구간 밖 3점 연속이면 알림.

결과 (`logs/faults.txt`). 탐지율 / 중앙 지연 / 고장 전 오탐:

| 경우 | 규칙 | Timestral-5M | Timestral-28M |
|---|---|---|---|
| 정상 (오탐 시리즈) | **0/40 (0%)** | 17/40 (42%) | 10/40 (25%) |
| 히터 열화 | **20/40 (50%)**, 8분, 0 | 14/40 (35%), 7분, 6 | 11/40 (28%), 7분, 1 |
| 센서 고착 | **40/40 (100%)**, 9분, 0 | 6/40 (15%), 4분, 1 | 5/40 (12%), 4분, 2 |
| 뚜껑 열림 | **38/40 (95%)**, 3분, 0 | 34/40 (85%), 2분, 4 | 35/40 (88%), 2분, 1 |

- 모든 고장에서 규칙이 탐지율과 오탐 모두 앞선다. Timestral이 나은 점은 탐지 지연 1분 정도뿐.
- 센서 고착은 고정값이 예측 구간 안에 머물러 모델이 거의 못 잡는다(구조적 한계).
- 히터 열화는 둘 다 약하다. 출력 50%로도 목표를 유지하는 기기는 듀티비만 늘어나 15분 단위 온도로는 드러나지 않는다.

### 4.4 예열 ETA: Timestral vs 직선/지수 피팅 (`scripts/eta.py`, `logs/eta.txt`)
설계:
- 시뮬레이션 100개. 수돗물 12~25℃ → 목표 55~63℃. 히터 3분 램프업, 0.1℃ 반올림.
- 20%는 가열 10~60분 사이에 재료를 투입해 2~4℃ 하락.
- 가열 시작 후 5/10/20/30분 시점에 남은 시간을 예측. 정답은 `target - 0.3` 도달 시각.
- 기준선:
  - 직선: 최근 5분 기울기
  - 지수(전체): 시작부터 `dT/dt = a - bT` 회귀
  - 지수(최근): 첫 3분 제외, 최근 15분만 사용
- Timestral은 since-start 컨텍스트(5~30점), 256분 예측, nosym. 중앙값 경로가 목표를 처음 넘는 시각을 ETA로 본다.

남은 시간 MAE (분). 남은 시간 중앙값은 68/62/52/42분. 5M 기준, 괄호는 재료 투입 제외:

| 시점 | 직선 | 지수(전체) | 지수(최근) | Timestral-5M | Timestral-28M |
|---|---|---|---|---|---|
| 5분 | **18.1** (17.7) | 18.1 (18.0) | 18.1 (18.0) | 35.4, 16% 실패 | 30.2, 87% 실패 |
| 10분 | 21.0 (20.7) | 21.3 (21.1) | 19.7 (19.6) | **15.1** (15.1) | 94.1, 81% 실패 |
| 20분 | 30.5 (16.6) | 27.5 (13.5) | 23.8 (9.9) | **11.1** (9.8) | 18.5 (16.6) |
| 30분 | 14.7 (12.5) | **9.3 (6.3)** | 15.8 (11.2) | 12.0 (11.6) | 15.5 (13.2) |

- Timestral-5M은 10~20분 구간에서 가장 낫다. 재료 투입에도 강하다(20분: 11.1 vs 지수 23.8).
- 5분 시점은 컨텍스트가 너무 짧아 실패가 많다. 30분 이후는 지수(전체)가 낫다.
- 28M이 5M보다 나쁘다. 짧은 컨텍스트에서 예측이 목표에 닿지 않는 경우가 많다.
- 80% 구간의 상한(q0.1 경로)은 10~20분 시점에서 거의 정해지지 않는다(0~1%). "18~24분" 같은 범위 표시는 30분 이후에만 일부 가능하다.
- 모든 방법이 초반에는 남은 시간의 25~35% 오차다. 사용자 기능으로 내보내기엔 거칠다.

## 5. 한계
- 데이터가 전부 시뮬레이션이다. 운영 Influx 데이터로는 검증하지 않았다.
- 규칙 임계값(1℃, 10분 등)은 시뮬레이터를 보고 정한 값이다. 실제 기기에서 다시 정해야 한다.
- 운영 서버에서 다른 부하가 거의 없을 때(load avg ≈ 0) 측정했다. 부하 테스트 중 수치는 없다.

## 6. 결론
- **지금은 도입하지 않는다.** oci1에서 5M은 돌릴 수 있지만, 이 데이터에서는 단순 규칙보다 탐지율이 낮고 오탐이 25~42%다.
- 먼저 규칙 기반 탐지(목표 이탈, 가열 정체, 센서 고착)를 순수 로직으로 구현한다.
- 규칙이 이 시뮬레이터를 보고 설계됐으니 규칙에 유리한 비교다. 다시 검토할 조건: 운영 데이터에서 규칙이 놓치는 이상이 실제로 확인될 때.
  그때 후보는 실시간 판정이 아니라 듀티비·가열 속도 같은 파생 지표의 일 단위 드리프트 감지다.

### ETA
- Timestral이 특정 구간(가열 10~20분)에서 기준선보다 낫지만, 우위가 좁고 범위 표시가 안 돼서 Python 사이드카를 들일 근거로는 약하다.
- 더 유망한 대안: 기기별 과거 예열 세션에서 출력·열 손실(a, b)을 학습해 두고 첫 분부터 지수식으로 계산. Java 순수 로직으로 충분하다. 실제 기기 이력이 필요하다.
- 시뮬레이터에서 a, b는 시리즈마다 무작위라 이 대안은 검증하지 않았다.

## 7. 재현
서버에 pip/venv가 없어 `uv`를 썼다. pip가 있으면 `python3 -m venv`로 대신해도 된다.

```bash
export UV_INSTALL_DIR=$PWD/bin UV_CACHE_DIR=$PWD/cache HF_HOME=$PWD/hf
curl -LsSf https://astral.sh/uv/install.sh | sh
bin/uv venv .venv
bin/uv pip install -p .venv torch --index-url https://download.pytorch.org/whl/cpu
bin/uv pip install -p .venv git+https://github.com/mistralai/timestral.git
nice -n 19 taskset -c 1 .venv/bin/python bench.py mistralai/Timestral-5M 1   # 모델, 스레드 수
nice -n 19 .venv/bin/python accuracy.py mistralai/Timestral-5M
nice -n 19 .venv/bin/python faults.py mistralai/Timestral-5M
nice -n 19 .venv/bin/python eta.py mistralai/Timestral-5M
```

- 실제 실행과 사본의 차이: 123M/209M 벤치는 `bench.py`에서 `ours batch32` 줄을 지우고 돌렸다. 209M 정확도는 `accuracy.py`의 스레드 수를 2로 바꿔 돌렸다(정확도는 스레드 수와 무관).
- 시뮬레이터 난수 시드는 스크립트에 고정돼 있다. 같은 패키지 버전(`logs/server-env.txt`)이면 같은 결과가 나와야 한다.
